## Current architecture and approved implementation shape
Store alone owns persisted/replayed lifecycle records and detour SQL. Each durable record completes append/fsync → readback → one DB projection transaction → typed DB reconstruction → value equality/byref-link assertions → cursor transition before the next record. This applies to pull/push exchanges, commit, captured model HTTP, validation, and run outcome; query response is ephemeral. No group rollback, buffering, fallback, or invalidation of a valid replay prefix. `current_replayed_record` is the only lifecycle cursor. Context owns frozen startup config/namekey/blueprints; Store never queries main DB. Byref nesting uses `is` where it is genuinely the same instance; a newly reconstructed or subclass-derived object compares by value, not `is`.

The operator-staged CAS model is exactly a `CASCodexRolloutRecord(CodexRolloutRecord)` with `cas_path: Path` and the operator's docstring; do not edit that class. `AiAugmentCAS.validated_rollout` now constructs it from `reference.sha256`, `size`, `line_count`, and the validated path. Consumers use inherited rollout fields, not my invented nested `.codex_rollout_record`; a subclass instance is distinct from the base reference. Existing direct CAS tests compare all inherited field values and path.

The approved post-commit evaluation boundary remains module-level `evaluate_commit(commit_request_record, *, initial_validation_request_record, inputs, db_reads) -> tuple[PostCommitValidation, _ValidationProjection]`. Do not remove its `initial_validation_request_record` argument, the validator's `TYPE_CHECKING` import, or `_CommitEvaluationInputs.original_pull_response_record` without a separately approved proposal. The imported concrete type is now `BackendValidationRequestRecord`. Store's `_validated_commit_inputs` prepares the same byref commit/initial validation lineage and lazy inputs for both live preview and replay application; validator knows no Store, SQL, or `AiAugmentSingularOuterDict`.
